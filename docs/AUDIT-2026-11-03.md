# 原生渲染与 Agent 创作链路审查

后续更新：原生 `.qppt` 封装与加载现已实现，不设版本字段，见 [QPPT](QPPT.md)。下文保留本次审查时的判断与性能基线。

日期：2026-11-03。基线提交：`4967438`。本轮以原生 XML 创作、Agent 看图改稿、用户直接预览和放映为目标，检查 core、CLI、WASM、Worker、预览器与回归测试。

原生渲染链路已经成立：XML 经过 Taffy 排版与 COSMIC Text 整形，直接由 Rust 绘制；WASM 使用同一实现。PPTX 是交付出口，不是预览所需的中间格式。当前可以支持静态原生阅览和点击步骤放映，尚不足以宣称完整的演示播放引擎。最重要的缺口是连续动画时间轴、客户端交付契约和移动设备性能验证。

## 能力与边界

| 用户目标 | 代码与实际结果 | 边界 |
|---|---|---|
| 接近 HTML/CSS 的创作语言 | `parser.rs` 严格解析 XML，`layout.rs` 使用 block/Flex/Grid；已有 Token、Style、Component、逐页文件与来源位置 | 是静态 CSS 子集；没有浏览器级级联、任意选择器、脚本和完整 CSS。不能直接接受任意网页 |
| Agent 不必读取 OOXML | 创作、测量、检查、逐页 PNG/PDF 均直接消费原生格式 | 导入现有 PPTX 仍是有限重建，不能恢复原来的组件或布局意图 |
| 按页迭代 | CLI `check/render --page <id>` 保留原页编号，本轮修复为只读取选中页的图片 | 仍解析整个项目 XML、加载共享字体；WASM 修改源码仍重新编译整个文稿 |
| 不启动 Office 的直接阅览 | Worker 内编译与绘制，静态 PNG 预览；新增 RGBA → Canvas 的展示路径 | 当前是 CPU 栅格化，不是 GPU 场景渲染；还没有正式客户端 SDK |
| 用户直接放映 | 本轮增加原生按步放映、键盘/触屏前后退、全屏与固定全屏容器回退 | 播放点击终态；duration/delay/easing/repeat 的中间帧及页面切换暂不播放 |
| 中间状态截图 | CLI `render --steps`、core/WASM `render_png_step/renderPngStep`；manifest 和 inspect 返回步骤数量 | 这是点击步骤，不是某个毫秒的动画采样；自动动画先结算进步骤 0 |
| 可编辑 PPTX 交付 | 已有原生文字、形状、图片、组、表格、图表与 OOXML timing | 未嵌入 PPTX 字体；Office 自行排版；没有任意文件无损往返或真实 PowerPoint/WPS 验收 |

## 本轮完成的改动

1. 把栅格化表面与 PNG 编码分开。Rust `render_rgba` 和 WASM `renderRgba` 返回 straight-alpha sRGB RGBA8；按步版本使用相同绘制实现。透明背景、抗锯齿边缘和非整数缩放的像素与 PNG 解码结果逐字节一致。
2. 复用不可变 `CompiledDocument` 提供 `step_count/stepCount`、PNG/RGBA 步骤渲染和放映元数据。静态页与步骤 PNG 共用原有 8 项 / 32 MiB LRU 预算，键包含步骤，互不混淆。RGBA 不缓存整页表面。
3. Worker 展示路径直接转移 RGBA ArrayBuffer；完整独占缓冲区不再额外 `slice` 一份。Canvas 放映按视口选择分辨率，退出时释放 backing surface。静态预览继续使用有缓存的 PNG。
4. CLI 逐张写入同文件系统的私有临时目录，全部渲染成功后独占创建目标目录并发布，manifest 最后发布。失败会清理临时目录；目标已存在或并发创建时不会覆盖。没有引入整套截图缓存。发布过程不是整个目录的一次原子替换，进程被强制终止可能留下不带 manifest 的目录，宿主应以 manifest 为完成标记。
5. 按需求一个步骤的状态，避免为仅需一张截图的 API 创建全部状态映射。CLI 不再同时持有全部状态 PNG。单步求值仍需要扫描此前动画，不是增量时间轴。
6. 修复组与子元素动画的组合错误。先前子元素的独立状态会覆盖组的位移、透明度或隐藏状态；现在同时组合两层位移/缩放、相乘透明度、继承隐藏状态。新增先失败后通过的像素回归。
7. CLI 先选择页面，再读取图片。其他页尚未准备好的图片不再阻塞当前页的检查与渲染；公共字体和 XML 语法仍整体检查。

原有 XML 语法、静态 PNG/PDF 与 PPTX 路径保持兼容。新增示例为 `examples/show.xml`，浏览器入口为 `examples/wasm-preview.html`。

## 性能实测

环境：macOS ARM64，Apple M4，16 GiB 内存，Rust 1.92.0。原始记录见 [性能数据](AUDIT-2026-11-03-performance.json)。下面的两组测试使用不同构建配置，不能交叉比较耗时。

### 100 页 CLI 内存

相同的 100 页图片文稿，`render --steps` 输出 300 张 PNG。前后均为 debug 构建，单次独立子进程，图片内容与尺寸固定。

| 指标 | 基线 | 优化后 |
|---|---:|---:|
| 峰值 RSS | 162.14 MiB | 26.89 MiB |
| 输出 PNG 总字节 | 131,669,500 | 131,669,500 |
| 耗时 | 105.39 s | 108.04 s |
| PNG 对比 | — | 300 / 300 逐字节一致 |

峰值 RSS 减少 **83.4%**。时间没有改善，临时目录发布还增加少量文件操作；这项改动的收益是降低内存。源文件、完整布局和 PDF 仍可能随文稿规模增长，不能把它解释为整个编译器的常量内存保证。此负载也不代表 100 页 CJK 文字或手机 WASM 压测。

复现：先保存基线和优化后二进制，再分别执行；输出目录必须不存在。

```bash
python3 tools/benchmark_render.py --cli PATH_TO_CLI --out target/my-benchmark --pages 100 --steps
```

### 原生像素输出

同一张 1280×720、12 行文字页。release 构建，前后交替运行五轮，每轮 100 次，表内为每轮均值的中位数；PNG 测试绕过编码缓存。

| 路径 | 每次耗时 |
|---|---:|
| 基线 PNG | 10.11 ms |
| 本轮 PNG | 9.63 ms |
| 本轮 RGBA | 3.62 ms |
| 本轮 PNG 缓存命中 | 约 0.001 ms |

RGBA 相对同版本未缓存 PNG 约快 **2.66 倍**。不能据此宣称整体 PNG 渲染显著提速，也不能当作浏览器端到端帧率：WASM/JS 拷贝、Worker 传输、Canvas 上传与屏幕合成未包含在此 native 计时中。该页 RGBA 为 3,686,400 字节，PNG 仅 80,157 字节；静态页重复查看时，缓存 PNG 仍更便宜。

```bash
cargo run --release --locked -p slide-shuttle-core --example render_benchmark -- 100
```

## 下一步优先级

| 优先级 | 问题及证据 | 建议的最小解决范围 |
|---|---|---|
| P0 | `show.rs` 的状态结算不按时间采样，`render.rs` 没有连续转场；PNG 步骤无法验证动画中途遮挡或轨迹 | 在 Rust 建立共享的 `sample(page, click, elapsedMs)`。先实现 fade、appear/disappear、线性移动、缩放及基础缓动；CLI 和 WASM 共用采样器。暂不实现的效果明确报告能力，不另写一套 JS 动画语义 |
| P0 | 原生工程是目录与显式资源，尚无版本化的客户端加载和播放契约；Deck 根节点没有格式版本字段 | 先稳定现有 project(files/assets/fonts) 的加载、版本/能力查询、生命周期及错误结构。桌面与移动 WebView 先共用 Worker/Canvas 适配；真正原生纹理宿主再接 Rust。PPTX 导出保持独立出口 |
| P1 | 内置两个 CJK 字体首次约 38 MiB；当前 web WASM 约 6.6 MiB，均为未压缩体积；`TextEngine::new` 复制字体，资源变化时可能重建字体系统 | 先做有许可和字重保证的字体分包、按需加载、HTTP 压缩与缓存。再拆分图片变化与字体系统失效，测量旧文档存活时的内存；不要先增加通用资源管理框架 |
| P1 | `render.rs` 每帧重新解码图片、解析字形轮廓；缩放/移动对象还分配整页透明层，组内对象可能重复分配 | 先用图片、文字、图表各一组 WASM profile 找主耗时；随后增加有字节上限的解码/轮廓缓存及复用 scratch surface。PNG 缓存的 32 MiB 不约束这些内存 |
| P1 | 任意 PPTX 不无损；字体嵌入缺失，复杂对象和母版仍有损；原生预览与 Office 不是同一排版器 | 明确“自创文稿支持集内可编辑导出”和“外部文稿有限导入”两类契约。补字体嵌入和真实 Office 编辑/保存样本；保留已有 losses/diff 保护 |
| P1 | 浏览器画布展示没有逐对象可访问性或交互覆盖层；本轮窄屏测试不能替代 iOS/Android 实机 | 先使用 inspect 的文字/备注/对象信息做宿主辅助内容和链接命中层，验证 VoiceOver/TalkBack、横竖屏、低内存恢复；不把浏览器截图当实机验收 |
| P2 | CLI fatal error 仍常为纯文本；源码改动通常全稿重编译；文档能力表落后于实现 | 统一 JSON 错误与能力查询，增加按页 WASM 编译入口；先稳定子集文档与诊断闭环，再考虑依赖图级增量编译 |

不建议现在引入完整 HTML/CSS 引擎、第二份前端排版树、任意 OOXML 原包 patch、或为每个客户端另造 DSL。保留 XML → 类型化模型 → 已定位 Scene → 统一栅格化的主线；把放映状态加入同一 Rust 核心即可。

## PPTD 路线的借鉴范围

用户提到的格式应为 **PPTD**。所查公开实现把主题、逐页结构和资源从 OOXML 中提取出来，Agent 编写简化 DSL，再生成可编辑 PPTX；这条工作流值得借鉴。其格式文档的概述声称无损互转，但同一项目的创作 Skill 明确写出 PPTX → PPTD 并非完全无损。因此，不能将“导出了可编辑 PPTX”直接作为任意文稿无损的证据。

公开 `Binaryify/open-kimi-ppt-skill` 自称非官方项目，已于 2026-08-07 归档，目前仅剩说明。其他分支的本地编辑器、patched WASM 与私有前端兼容协议不能作为本库稳定运行时的基础。这里借鉴逐页自包含、Agent 可写、预览复核、可编辑交付的产品思路，不复制其格式或运行时。

## 验证范围

本轮运行 Rust workspace 测试、严格 Clippy、fmt、wasm32 目标检查、实际 release WASM 构建、Node WASM 冒烟、JavaScript/Python 测试与真实 Chromium + Worker 回归。

- RGBA 与 PNG 解码像素一致，覆盖透明度、非整数缩放、无效页码/比例、非法布局。
- 步骤与静态 PNG 缓存隔离，文档在 Compiler/Engine 释放后仍可绘制。
- 原生与 WASM 中文示例 PNG 逐字节一致；步骤 PNG 与 CLI 逐字节一致。
- Chromium 156 验证键盘/触屏步骤前后退、跨页、退出、PNG 下载与窄屏画布。现有导入、字体替代、取消恢复回归继续通过；无页面异常或外部网络请求。
- 临时输出失败清理、并发目标保护、单页图片加载与原页编号有回归测试。

原始运行产物留在忽略 Git 的 `target/audit/` 与 `examples/output/`；性能摘要纳入本目录。Safari/Firefox、真实 iOS/Android、100 页 WASM 总内存、连续动画与 PowerPoint/WPS 仍未验收。
