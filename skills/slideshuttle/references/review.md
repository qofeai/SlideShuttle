# 通过渲染结果改稿

构建产物只说明引擎能处理文稿。以下判断需要真实查看 PNG，不能从 XML 或 build.json 推断。

## 先看全稿，再看每页

用 contact-sheet.png 或 index.html 检查叙事顺序、构图节奏、色彩和文字层级是否一致。然后逐页查看完整 PNG，特别是高密度内容、CJK 混排、小字、图片裁切和图表标签。只有缩略图时，不声称已核对正文可读性。

| 维度 | 看什么 | 常见修复 |
|---|---|---|
| 观点与证据 | 标题是否有清楚含义；主体是否真的支持标题 | 改写标题、重排证据、删去无关装饰 |
| 视觉主次 | 第一眼看到了什么；主视觉与辅助文字是否争抢 | 调整区域大小、字号、对比与位置 |
| 文字 | 意外孤行、拆词、挤满、过小、低对比 | 改写、增大可用空间、重新分栏或拆页 |
| 对齐与关系 | 同类内容是否靠近；基线/边缘是否有意一致 | 调整容器、gap、padding 与文字高度 |
| 图表 | 单位、刻度、图例和关键差异是否清楚 | 简化系列、增大图表、把解释靠近数据 |
| 图片与图示 | 裁切是否丢失主体；箭头/分支是否表达关系 | 调整 fit、替换构图或简化连接 |
| 全稿节奏 | 是否所有页都重复同一个版式；密度是否合适 | 依内容换用对比、图表、关系图或强调页 |
| 放映 | 有动画的页用 `render --steps` 逐步查看：第一步是否空得合理，每次点击是否只多出一组相关内容 | 合并零碎的点击、把同时出现的元素放进 Group 或改为 with-previous |

为具体缺陷做具体修改。不要把每次编译变绿描述为视觉质量上升，也不要在没有评测的情况下宣称达到某排行榜或某产品的审美水平。

## 错误与警告

- text_overflow：先检查实际内容、字体、框尺寸和行数，再处理版面。文本宽度是字体几何，不是字符个数。
- text_tight：文字框余量很小；检查导出环境和换行。保留正文换行，给窄标签合理的留白。
- out_of_bounds：检查定位、父盒子、边距与装饰边界；不要直接把对象移到画布外来藏内容。
- font_substitution：浏览器使用了替代字体；原字体与替代字体的换行可能不同。CLI 创作稿优先使用明确提供的字体，保持可复现。

修复结构问题后重新构建，检查修改后的页。若变动影响共享样式/组件或整套节奏，再查看全稿。一个局部问题已解决且没有新问题时，继续交付，避免无理由地重复全套检查。

## 完成与报告

交付用户要求的文件，并用简短说明记录采用的设计方向、实际检查范围和重要限制。确实查看了所有页面，才能说“已逐页检查”；确实运行了 Office/WPS，才能给出对应应用结论。没有视觉工具时，说明已完成编译/产物检查以及尚未完成的视觉复核。

原生 PNG/PDF 和 PPTX 由不同排版链路呈现。图表的绘图区、图例和刻度已固定，但字体与折行在 Office 里仍可能不同。需要高保真交付验收时，在目标应用独立渲染并比较，不把原生预览当作其替代证据。
