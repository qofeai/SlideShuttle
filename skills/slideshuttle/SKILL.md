# 用 SlideShuttle 设计演示稿

把演示文稿当作**视觉论证**，而不是“贴在 16:9 墙上的 Word 讲义或密集信息看板”。用多文件静态 XML 工程表达结构与重点，把口语推导放进 `<Notes>`，交给原生引擎排版、渲染并交付可编辑的 `.qppt` / `.pptx` / `.pdf`。

---

## 一、 五大美学与信息密度红线（落笔前必检）

无论用户要求内容多么“严谨详细、从零推导”，**严谨性必须通过“拆细页数 + 精确图形/公式 + 详细 `<Notes>` 讲稿”实现，严禁在单页画布上堆砌小字与套娃方框。** `scripts/build.py` 会自动审计以下指标：

| 维度 | 硬性标准（1280×720 画布） | 常见反例（严禁出现） |
|---|---|---|
| **1. 字号硬底线**<br/>*(3 秒可读)* | • 视觉锚点（大数字/核心公式）：**`56px–120px`**<br/>• 页面主标题（结论句）：**`40px–52px`**<br/>• 栏标题 / 卡片标题：**`26px–32px`**<br/>• 正文 / 要点列表：**`20px–26px`（严禁 `< 20px`）**<br/>• 图注 / 表格单元格：**`16px–18px`（严禁 `< 16px`）** | 为了塞下长段文字且不触发 `text_overflow`，把正文字号缩到 `12px–15px`。放不下时必须**删减字数或拆成两页**。 |
| **2. 单页字数与文风**<br/>*(画面与讲稿分离)* | • 单页画布可见文字（不含 `<Notes>`）：**60–150 字（绝对上限 220 字）**<br/>• 单个文本框最多 **1–3 行**，一律使用**电报式短语**，删去“因为…所以…”、“当…时”等口语连接词<br/>• 完整推导、举例和过渡语全部写进 **`<Notes>`** | 把讲义原封不动搬上屏幕，单页出现 300–500 字的多行自然段，迫使观众低头默读。 |
| **3. 留白率与去框/去页脚**<br/>*(呼吸感 ≥ 40%)* | • 画布留白率 **≥ 40%**（外边距 `48–64px`，主分栏 `gap: 36–56px`）<br/>• 单页渲染节点数 **≤ 26 个**，并列模块/卡片 **≤ 3 个**（上限 4 个）<br/>• **严禁默认添加页码（如“第 X/Y 页”）、装饰性页脚或工具署名（如“由 SlideShuttle 渲染”）**，除非用户明确要求 | “大框套中框、中框套小框（Box-in-Box）”，或在每页底部画蛇添足地加上页码、口号式页脚、工具水印。 |
| **4. 单一视觉焦点**<br/>*(主次分明)* | • 每页有且仅有 **1 个主角**（占 50%–65% 视觉权重：巨型关键数字、一张大图表、或一个核心流向图）<br/>• 其余文字仅作为主角旁边的简短批注 | 页面上所有方框面积相等、字号相近，处处是重点等于没有重点。 |
| **5. 色彩克制**<br/>*(高级感)* | • 除黑白灰（背景、主文字墨色、次级灰）外，**单页强调色只用 1 种**（正反对比页最多 2 种） | 同一页同时出现蓝框、绿框、黄框、红框，像彩虹贴纸一样杂乱。 |

## 二、 从信息关系选构图（拒绝千篇一律的卡片模板）

根据每页要传达的逻辑关系选择构图，连续两页不要重复完全相同的版式：

| 信息关系 | 推荐构图（1280×720） | 视觉主角 |
|---|---|---|
| **开场 / 章节主张** | 深色或高对比背景，左 7 右 5 非对称分栏，大标题 + 1 个核心视觉图或 3 个极简大数字 | `52px–66px` 主张标题 + 几何主视觉 |
| **核心概念 / 公式直觉** | 上方 1 个大号核心公式/图形框（占 55% 高度），下方 2–3 列无边框短语对应拆解 | 屏幕中央的大公式或向量几何图 |
| **前后对照 / 瓶颈突破** | 左右 `5fr 7fr` 或 `1fr 1fr` 鲜明对比（左：旧方案痛点/灰色；右：新方案突破/强调色） | 数量级差异（如 `389 GB → 0.89 GB`） |
| **架构流向 / 因果机制** | 单一画布关系图（3–5 个核心节点 + 箭头连接），右侧配 2 条精炼结论 | 占 60% 宽度的结构流向图 |
| **数据与实测证据** | 大尺寸 `Chart`（占 60% 宽度）+ 紧邻的 `80px+` 核心指标与 2 条结论短语 | 图表本身与最高得分数字 |
| **多维演进 / 总结对比** | 干净的宽幅 `Table`（控制在 4–5 行 × 4 列以内，单元格仅放短语）或 3 步行动路线 | 高亮的目标行（如最新一代架构） |

## 三、 极简三步工作流

### 第 1 步：规划页序与共享设计系统
1. 先定每页的**唯一核心判断**和**视觉主角**。若内容复杂，**宁可拆成 12–15 页清爽的幻灯片，也不要挤压成 8–10 页密集的讲义**。
2. 所有文稿按多文件工程组织（参考 [assets/starter/](assets/starter/deck.xml)，语法细则见 [语法与排版速查](references/authoring.md)）：
   ```
   deck/
     deck.xml          # 入口：尺寸、字体、<Library src="design.xml"/>、按序排列的 <Slide src="..."/>
     design.xml        # 共享 Token（主墨色/背景/单一强调色）、Style（标题≥40px、正文≥20px）、Component
     pages/01-cover.xml
     pages/02-claim.xml
     icons/            # 可用 python3 scripts/icons.py <name>... --out deck/icons 复制单色 SVG 图标
   ```
3. 页面元素 `id` 只需在本页内唯一。多页可并行撰写：主 Agent 先固定 `deck.xml` 与 `design.xml`，再按页编写 `pages/*.xml`。

### 第 2 步：构建并清零“编译错误 + 美学密度警告”
从本 Skill 目录运行：
```bash
python3 scripts/build.py --doctor
python3 scripts/build.py /path/to/deck/deck.xml --out /path/to/output/v1
```
- 脚本自动生成 `presentation.qppt`、`presentation.pptx`、`preview/deck.pdf`、逐页 PNG、`index.html`、`contact-sheet.png`（装有 Pillow 时），并输出包含 **`diagnostics`**（排版错误/警告）与 **`designAudit`**（字号、字数密度、节点数、行数审计）的 JSON 报告。
- **单页快速自检**：修改单页时可用 CLI 快速检查该页：
  ```bash
  slide-shuttle check /path/to/deck/deck.xml --page <slide-id> --font ...
  ```
- **触发 `text_overflow` 或 `designAudit` 警告时的修复铁律**：
  1. **先删减冗余字词、改为短语，或把长句移入 `<Notes>`**；
  2. **再调整容器空间分配或拆分为两页**；
  3. **严禁通过把正文字号缩到 `< 20px` 来消除溢出！**

### 第 3 步：逐页看 PNG 视觉复核与交付
1. 编译和脚本审计通过后，**必须用读图工具逐页查看渲染出的完整 PNG**（先看 `contact-sheet.png` 检查全稿节奏与版式变化，再逐张看 `preview/slide-*.png`）。
2. 对照 [视觉复核与改稿清单](references/review.md) 检查：第一眼焦点是否明确、留白是否充裕、是否有跨行孤字/拆词（如引号挤出单字）、对齐与基线是否干净。
3. 改稿后用新目录（如 `v2`）重新构建并复核修改页。
4. **交付**：优先交付原生 `presentation.qppt`（内嵌源码、字体与资源），并按需附上 `presentation.pptx`、`deck.pdf` 与预览图，如实说明设计取舍与已验证范围。
